Why it counts as “less used” Part A

Being honest about this matters more than winning the argument: it is not obscure. 1.47 million installs a week is a lot. The case is comparative.

@playwright/mcp 6,364,011
chrome-devtools-mcp 1,465,302
server-filesystem 954,129

npm downloads, week of 2026-08-31 → 09-06, via api.npmjs.org.

Three things carry the “less used” claim:

It loses 4.3 : 1 to the obvious pick. When people decide to let an agent use a browser, they install Playwright. Almost nobody installs a profiler.

It is not a reference server. The modelcontextprotocol/servers README does not mention Chrome at all — I grepped it, zero hits. It is vendor-shipped and third-party, exactly the category the brief points at.

It is missing from the marketplace people browse. Keyword searches on Smithery's registry API for chrome-devtools-mcp, devtools and playwright returned unrelated third-party servers. Smithery's search is fuzzy so I won't call it definitively unlisted — but it isn't findable there the obvious way. Distribution is npm, the official registry, and Chrome's own docs.

And the half that is popular is the boring half: the tutorials use navigate_page and click — the Playwright-shaped subset. The performance_*, heap-snapshot and emulate tools, the reason this server exists, are the part nobody touches. Both tasks below live there deliberately.

Setup Part C1 · nothing to redact

One command, project scope. There is no API key, no OAuth, no account — this server has no auth surface at all, so there is no secret in this dossier to redact. 

$ claude mcp add chrome-devtools --scope project -- \
    npx -y chrome-devtools-mcp@1.8.0 --headless=true --isolated=true
PieceWhat it actually does
"type": "stdio"Client spawns the server as a child process and speaks JSON-RPC 2.0 over stdin/stdout. No port, no daemon — the browser dies with the session.
npx -yRun without a global install. -y skips the install prompt, which would otherwise hang a stdio server forever waiting on a stdin the protocol is already using.
@1.8.0Pinned deliberately. The docs say @latest. On a tool that spawns a browser and reads every response body, I don't want npx pulling a new major on a random Tuesday.
--headless=trueNo visible window. Turn it off to watch the agent work — genuinely useful when debugging the debugging.
--isolated=trueTemporary profile, deleted on close. The default is not your everyday Chrome — it's a persistent dedicated profile at $HOME/.cache/chrome-devtools-mcp/. So the risk it removes is accumulation: log into staging once and that cookie waits there for the next session.

The gotcha that actually blocked me

A project-scoped server is inert until the folder is trusted. Straight after adding it, the health check said ⏸ Pending approval — and shipping .claude/settings.json with enabledMcpjsonServers did not change that, because committed approvals are ignored until you run claude in the folder and accept the trust dialog. Once I did: 

$ claude mcp list
Checking MCP server health…

chrome-devtools: npx -y chrome-devtools-mcp@1.8.0 --headless=true --isolated=true - ✔ Connected

Worth naming as a security point rather than a footnote: that prompt exists so a human vets a server before it runs. Committing the approval trades that review for convenience — fine for a team that already vetted it, wrong as a default.

Four smaller ones cost me time, all schema surprises: pageId is a number though list_pages prints it as 1:; viewport is a string "412x915", not an object; extraHttpHeaders is a JSON string, not an object; and console types wants "warn", never "warning".

Task 1 — is this docs site fast on a mid-range phone? Part C2

A real question with a real answer. Emulate a throttled Android, record a trace across a reload, then drill into the insights — the workflow no other MCP server offers.

LCP breakdown · modelcontextprotocol.io/docs 4× CPU throttle · Slow 4G · 412×915
render delay — 1,761 ms · 98.2%
TTFB 33 ms · 1.8%
Render delay 1,761 ms · 98.2%
LCP 1,794 ms · CLS 0.00
The page is not network-bound. The bytes arrived in 33 ms; the browser then spent 1.76 seconds executing JavaScript instead of painting. The fix direction is “ship less JS, earlier” — not “add a CDN”. The LegacyJavaScript insight then named 24.9 kB of that as transpiler polyfills for Array.prototype.at, Object.hasOwn and friends: a build-config change with a measurable payoff, found without opening a browser.

The lab-vs-field split is the other genuinely useful thing: my throttled lab number (1794 ms) is worse than what real users see (CrUX p75, 1256 ms), which correctly says don't panic — my 4× throttle is harsher than the median visitor. It also means the URL I profiled was sent to Google's CrUX API. Fine for public docs; not fine for an internal staging URL, where the URL itself is the leak.

Task 2 — the list renders “Loading…” forever Part C2

A classic front-end bug hunt against a small local app with two planted defects. I never opened a browser or read the source to diagnose it — only Console and Network.

Stage 1 — the symptom

=== list_console_messages ===
msgid=1 [error] Failed to load resource: the server responded with a status of 404
msgid=2 [error] Uncaught (in promise) (0 args)
  at render (app.js:6:6)

=== list_network_requests ===
reqid=1 GET http://localhost:8931/          [200]
reqid=2 GET http://localhost:8931/app.js    [200]
reqid=3 GET http://localhost:8931/api/todos [404]

=== take_snapshot ===
uid=1_1 heading "Todo board" level="1"
uid=1_2 StaticText "Loading…"

Diagnosis: /api/todos 404s. The route is /api/todo-list.

Stage 2 — 200, and still stuck

The fetch now succeeds but the page hasn't changed, and the console error is uselessly terse. So I pulled the actual payload off the wire: 

=== get_network_request {"pageId":2,"reqid":3} ===
## Request http://localhost:8931/api/todo-list
Status: 200
### Response Body
{"todos":[{"id":1,"title":"Write MCP assignment","done":false}, … ]}

The payload key is todos. Line 6 of app.js reads data.items. undefined.map(...) — that is the Uncaught (in promise). Fix: data.items → data.todos.

Stage 3 — verified, not assumed

=== take_snapshot ===
uid=1_2 StaticText "⬜ Write MCP assignment"
uid=1_3 StaticText "✅ Run a perf trace"
uid=1_4 StaticText "⬜ Ship the write-up"

=== evaluate_script ===
{"rendered":3,"text":"⬜ Write MCP assignment\n✅ Run a perf trace\n⬜ Ship the write-up"}

=== list_console_messages {"types":["error","warn"]} ===
msgid=1 [error] Failed to load resource: 404 (Not Found)   ← ?

One honest loose end: that remaining 404 is not the bug returning. I checked instead of assuming — an unfiltered list_network_requests shows reqid=4 GET /favicon.ico [404]. My toy server has no favicon. Worth saying out loud, because “verified fixed, one unrelated 404 remains, here's what it is” is the actual standard — and my filtered query had hidden the answer from me.

Three experiments to check my own claims beyond the brief

Writing the “when to use” section meant asserting things like curl couldn't have told you this. Those are cheap to test, so I tested them instead.

Experiment 01

Could curl have answered Task 1?

$ curl -w "ttfb=%{time_starttransfer}s total=%{time_total}s bytes=%{size_download}"
attempt1  ttfb=0.267102s  total=0.306945s  bytes=89132
attempt2  ttfb=0.280781s  total=0.307872s  bytes=89132
attempt3  ttfb=0.213605s  total=0.247151s  bytes=89132

curl's verdict on the exact page from Task 1: responds in ~0.25 s, ships ~87 kB, nothing to fix. The trace's verdict on the same page: 98.2% render delay. Both are correct; they measure different things. Render delay happens after curl has hung up — so the cheap tool isn't a weaker version of the expensive one here, it is blind to the actual problem. That cuts both ways, and it's the basis for both sections below.

Experiment 02

Does --slim really shrink the surface?

### default            ### with --slim
tool count: 29          tool count: 3
                        evaluate, navigate, screenshot

=== tools/call list_pages {} ===
MCP error -32602: Tool list_pages not found

Confirmed — plus a detail the docs omit: the slim tools are renamed, not a subset. evaluate / navigate / screenshot, not evaluate_script / navigate_page / take_screenshot. So --slim is not a drop-in for an existing prompt or tool allowlist.

Experiment 03 · changed how I'd configure it

Does --redactNetworkHeaders actually protect credentials?

I used emulate to inject a fabricated bearer token and cookie, reloaded, and read the request back — identical steps, two server configs: 

### A) the default config, the one everybody copies from the README
## Request http://localhost:8931/
- authorization:Bearer FAKE-DEMO-TOKEN-NOT-REAL
- cookie:session=FAKE-DEMO-SESSION

### B) same, plus --redactNetworkHeaders
## Request http://localhost:8931/
- authorization:<redacted>
- cookie:<redacted>

By default, every credential on the page reaches the model in plain text. The flag works, it covers authorization and cookie, and it is off unless you ask for it. Nothing in the README nudges you toward it — I only found it by reading docs/configuration.md.

When I'd reach for it — and when I wouldn't Parts D4 · D5

Reach for it

A performance regression that only shows on real hardware. A PR lands, mobile LCP goes 1.9 s → 3.4 s, nobody reproduces it on a MacBook.

  • A Lighthouse score says 3.4 s, bad — a number, not a cause.
  • Playwright MCP can drive and screenshot the page, but has no trace recorder, so it can't say where the 1.5 s went.
  • curl measures the server, which in Task 1 was 1.8% of the problem — measured, in experiment 01.

This server closes the loop in one session: throttle → trace across reload → LCP split into subparts → insights naming the render-blocking requests, third parties and polyfill bytes → fix → re-trace. That's the DevTools workflow minus the human clicking, and it yields a cause with an estimated saving.

Second clear win: any bug whose evidence lives in the browser, not the source — a path typo, API contract drift like Task 2's items/todos, a CORS preflight, a leak via take_heapsnapshot + compare_heapsnapshots. Reading source to find those is guessing; reading the response body is knowing.

Don't

“Check the deploy is live and the API returns the right JSON.” Use curl. Booting Chrome costs ~5 s of startup, hundreds of MB of RAM and thousands of tokens of tool output — to learn what a 200-byte response already said.

In fairness, Task 2's stage-1 diagnosis was one curl away too. The server earned its place at stage 2, not stage 1.

  • You need to drive a browser, not measure one — multi-step forms, auth journeys, cross-browser. Playwright MCP is better and covers Firefox and WebKit, which this explicitly does not (Chrome and Chrome for Testing only).
  • You already have a failing test. If the assertion pins the bug, a browser adds only latency.
  • The page needs your logged-in production session. --isolated gives a blank profile; the workaround, --browserUrl onto your real Chrome, is the thing to think twice about.
  • CI with no Chrome binary. Hard dependency, not a fallback.

Best practices & what it touches Part D6

Local-only, unauthenticated, no rate limit, no per-call cost. That makes it feel harmless, and that impression is the risk. The README is blunt: it “exposes content of the browser instance to the MCP clients allowing them to inspect, debug, and modify any data in the browser or DevTools.”

Concretely an agent holding these tools can read full response bodies including Authorization and session cookies, run arbitrary JS in page context, dump the JS heap, and click or submit anything on screen. There's no OAuth-style scope system — but it is not all-or-nothing either:

ControlDefaultEffect
--redactNetworkHeadersfalseTurns Authorization and Cookie into <redacted> — verified in experiment 03.
--slimfalse29 tools → 3 — verified in experiment 02. Far smaller blast radius when you only need to look at a page.
--no-performance-cruxCrUX onStops trace URLs going to Google's CrUX API. The field-data block in Task 1 is that call happening.
--no-usage-statisticsstats onOpts out of Google's usage collection.
--filesystemRootOS tempBounds where file-writing tools may write. Without negotiated MCP roots, writes are temp-only by default.

A supply-chain note I stumbled on: searching the official MCP registry for “chrome-devtools” returns two results — the real io.github.ChromeDevTools/… and a look-alike io.github.Async23/… publishing @async23/chrome-devtools-mcp under the same description. Being in the registry is not the same as being the package — verify the npm identifier and GitHub org before installing something whose whole job is reading everything in your browser.

And treat page content as untrusted input. Response bodies and console text come from whatever site you loaded; an attacker-controlled page can print instructions aimed at the agent. Read them as data, never as commands.

The failure mode I actually hit

Console errors arrive stripped of their message text. The real error in Task 2 stage 2 was a TypeError: Cannot read properties of undefined (reading 'map'). What both list_console_messages and the detail call get_console_message reported was: 

msgid=1 [error] Uncaught (in promise) (0 args)
  at render (app.js:6:6)

(0 args) — the exception object never crossed the wire. An agent trusting the console alone would have a location and no cause, and would very plausibly start guessing at line 6.

The guard: never let the console be the sole source of truth. Corroborate from a second tool — get_network_request gave me the body, and {"todos":[…]} against a line reading data.items made the TypeError obvious without ever seeing its text. Generalised: console tells you where; network and evaluate_script tell you why. Where the text genuinely matters, wrap the call site yourself: evaluate_script with () => { try { … } catch (e) { return e.message } }.

Run it yourself one command

From the project root — Windows:

run.cmd

macOS, Linux or Git Bash:

./run.sh

It installs the pinned server if needed, starts the demo app, replays Task 1 and all three stages of Task 2 with a banner before each saying what to expect, restores app.js to its broken state, and stops the server. No second terminal. run.cmd task1 or run.cmd task2 narrows it.

Verified from a clean copy of the folder, twice. Task 1 profiles a live site, so its numbers move between runs — a later run measured LCP 2,704 ms with 99.0% render delay: different figure, identical conclusion.
